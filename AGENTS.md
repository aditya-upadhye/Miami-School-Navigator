# AGENTS.md

This app was generated by Archie from a prototype. It's a real, editable codebase — React 19,
Vite, TypeScript, Tailwind CSS 4, and shadcn/ui — talking to its backend through a generated SDK:
a live GraphQL API once a backend exists, or an in-memory adapter behind the same interface
before it does. Either way, routes and forms are wired to a real data contract, not a mockup.

## Commands

```bash
bun install          # install dependencies (Bun, not npm/yarn/pnpm)
bun run dev           # dev server, http://localhost:3000
bun run build         # eslint (LAWS only) + tsc -b + vite build (a law violation fails the build)
bun run build:check   # tsc --noEmit + vite build (fastest way to prove the tree still compiles)
bun run build:fast    # vite build only, no type-check — for quick iteration, not for verification
bun run lint          # eslint . (generic rules + the laws, see "Lint laws" below)
bun run lint:laws     # the laws only (eslint -c eslint.laws.config.js .) — exactly what build runs
bun run test          # unit tests (bun test, built into Bun — no extra dependency)
bun run preview       # serve the production build locally
```

Unit tests run with `bun run test` (Bun's built-in runner). Test files (`src/**/*.test.ts`) are
excluded from `tsconfig.app.json`, so the app build never type-checks `bun:test`.

Always use `bun run <script>`, not `bun <script>` for `build` — `bun build` is Bun's own bundler
and will not run the npm script.

## Which shape is this app?

Generation has two output shapes, chosen at generation time (`EMIT_SHAPE`), and you're always in
exactly one:

- **Layered** — `src/presentation/`, `src/application/`, `src/domain/`, and
  `src/infrastructure/archie/` exist. `presentation → application → domain`,
  `infrastructure → domain`. `domain/` never imports React, the SDK, or an HTTP/GraphQL client. A
  view or container never imports the SDK directly — it reads identity/data through a domain
  **port**, and `infrastructure/archie/` is the adapter that implements it (some screens instead
  run on an in-memory adapter behind that same port, with no live backend). This is what lets a
  view be tested or reused without a real backend.
- **Flat** — no `presentation/`/`domain/` split; screens live at `src/screens/<slug>.gen.tsx`, but
  the SDK doesn't appear in the screen file itself — it enters through generated hooks under
  `src/hooks/*.gen.*` and the chrome modules `src/lib/gen/role-nav.gen.ts`/`shell-user.gen.ts`.

Besides `main.tsx` (the composition root — constructs the client, mounts the providers everything
else consumes), the generated, sealed `src/lib/gen/preview-auth.gen.tsx` (the preview-iframe auth
handshake) imports the SDK directly in both shapes, but only when a real backend is wired. In the
layered shape specifically, `src/app/auth-guard.gen.tsx` (the route guard) does the same when a
real backend is wired — re-exporting the SDK's own `AuthGuard` — or, without one, a plain
`useIdentity()` guard with no SDK import at all.

## `src/App.tsx` and `src/main.tsx` are immutable

They own the router shell, error boundary, and the SDK/theme/query providers. Regenerating this
app never touches them, and neither should you.

## Lint laws (they run in `build`)

Two architectural laws are enforced by `eslint.laws.config.js`. `bun run build` runs ONLY that config
(`lint:laws`) before `tsc -b`; `bun run lint` is the full developer config (the laws plus generic
`react-hooks` / `typescript-eslint` rules, which do not gate the build):

- **Hexagonal boundaries** (`eslint-rules/boundaries/config.js`): `presentation → application →
  domain`, `infrastructure → domain`; `domain` is pure (no React/SDK/graphql/HTTP client); only
  `src/infrastructure/archie/**` imports `@archie/js-sdk` / `@archie/react-sdk` (the composition root
  `src/app/**` takes `AuthGuard` and `useArchieClient` only, plus `import type` from the js-sdk).
- **The view law** (`eslint-rules/archie-view-law`, local plugin): files under
  `src/presentation/views/**` call only the allowlisted hooks (never `useEffect`), reach no data /
  router / infrastructure, derive nothing from entity arrays, and use no `as` (except `as const`) or
  `any`.

**Transplanted views (`*.view.jsx`): `.jsx` under L37 (boundaries), outside the view law** (gv2's gate C +
AST assertions police transplanted views). `generate-frontend` transplants prototype JSX verbatim as
`src/presentation/views/**/*.view.jsx` (+ emitted `.d.ts`). The boundaries lint covers `src/**/*.{ts,tsx,js,jsx}`
(a `.jsx` view importing the SDK or infrastructure fails); `VIEW_GLOBS` stays `*.{ts,tsx}` ON PURPOSE: widening it
without a whole-read marker would make every transplanted view trip `no-entity-derivation`. The emitted
`*.view.d.ts` IS under the view law. Details: `eslint-rules/archie-view-law/README.md` ("Transplanted views").

**`archie.view-law.json`** (template root) is the single source of the view-law allowlists (also read by
apg's build:lib -> catalog.json): import prefixes/exact specifiers, import bans, allowed hooks. The rules
read it at lint time; change the allowlist there, nowhere else.

`src/client/**` is the survivor zone (see its README) and has no lint restrictions. Fix the code,
not the config. Path conventions the laws rely on: `eslint-rules/archie-view-law/README.md`.

## Self-hosted fonts (`public/fonts/`)

Drop `.woff2` files in `public/fonts/` (Vite serves `public/` verbatim, so `public/fonts/Inter.woff2`
is `/fonts/Inter.woff2`; the folder ships empty). Declare each face in a stylesheet with an absolute URL:

```css
@font-face {
  font-family: "Inter";
  src: url("/fonts/Inter-Variable.woff2") format("woff2");
  font-weight: 100 900;
  font-display: swap;
}
```

One block per weight/style for static files. Preload only the above-the-fold face
(`<link rel="preload" href="/fonts/…" as="font" type="font/woff2" crossorigin>`, `crossorigin` is
required even same-origin). Check the licence before committing a font.

## Skeleton screens — one module per view

`src/presentation/views/<slug>.view.*` is ONE module: either `<slug>.view.tsx`, or `<slug>.view.jsx` + `<slug>.view.d.ts`. Never create a `.tsx` next to a `.jsx` — Vite resolves `.jsx` first and the import breaks. A view whose route imports it directly and has no `containers/<slug>.container.tsx` is an unbuilt placeholder: do not edit or delete it by hand; it is built by screen generation. To change a real view, edit it in place; a container imports `{ <Slug>View }` from `../views/<slug>.view` without extension.

Skeleton kinds and their markers:

- Plan card: `<slug>.view.jsx` + `<slug>.view.d.ts`, default export, `data-archie-plan-card="v1"`.
- Placeholder: `<slug>.view.tsx`, default export, `data-archie-placeholder="sin-convertir"`. An error placeholder additionally carries `"pantalla-error"`.

A real screen is: route -> `containers/<slug>.container.tsx` (default export) -> `views/<slug>.view.*` (named `<Slug>View`).

To turn a skeleton into a real screen, ask Archie to generate it; screen generation replaces the skeleton for you (container + view, route repointed, skeleton files removed in one commit).

Why: the route lazy-imports `./presentation/views/<slug>.view` with no extension, and a second file on the same base makes Vite and `tsc` disagree (tsc also collides a `.d.ts` with a `.ts`/`.tsx`). `vite-plugins/one-module-per-specifier.ts` enforces it: it fails `vite build` and shows an error in dev when two files share a base.

## The repo has two zones — know which one you're editing

`.archie/conversion.gen.json` names every path the last conversion produced, with a hash of its
bytes. **Anything it names is regenerated by the platform, not by hand here**: the next conversion
REPLACES every named path, so a hand edit or deletion there is lost, not refused. The previous tree
is saved on an `archie/backup/<UTC>-<rid8>` branch. A conversion refuses to run only when its
`expectedHeadSha` pin is stale (the repo moved since it was measured). Anything the manifest does *not* name is yours,
untouched by every future conversion. Before hand-editing an existing file, grep its path in that
manifest; when in doubt, add a new file instead of editing one you find there.

`src/components/kit/**`, `src/routes.config.tsx`, and every generated screen/i18n artifact below
are typically named in the manifest. To change a component, add a screen, or add a route, use
Archie's own chat/editor — it regenerates the named files and re-seals them. You can still write
brand-new files anywhere (a new hook, a new util, a new component that composes the ones under
`components/kit/`) — those aren't in the manifest and are always yours.

## The component plane (`src/components/kit/**`)

This project's own copy of its design-system components (buttons, cards, layout primitives, data
grids…) — a real local copy, not a vendored package, imported as `@/components/kit/components`.
It's part of the sealed zone above: request component changes through the platform rather than
hand-editing files here. `.jsx` files ship a paired `.d.ts` sibling; if you do add a file of your
own that changes what the barrel exports, keep both in sync or the bundler and TypeScript will
disagree about the module's shape. `src/styles/kitd/vendor.css` is this plane's base stylesheet,
generated alongside it.

## Colour mode: one per-app browser key, applied before first paint

The light / dark / system choice is stored in the BROWSER only (no server state), so two Archie apps on one domain must not share it. Rules, identical in `src/lib/theme-key.ts` and in the inline `archie:theme-init` script of `index.html` (`theme-key.test.ts` runs the script against the functions in every case):

- **Key**, first match wins: (1) `<html data-theme-key="<id>.theme">` when it matches `^[A-Za-z0-9_-]{1,64}\.theme$` (apg prototypes: the lib is built once for all projects, so there is no per-project env); (2) `<VITE_ARCHIE_PROJECT_ID>.theme` when that id matches `^[A-Za-z0-9_-]{1,64}$` (generated apps); (3) `app.theme`. An invalid attribute is ignored, not repaired.
- **Initial mode**, first match wins: the stored value under that key if it is `light|dark|system`; else the first valid legacy value (`archie-ui-theme`, then `archie-theme-mode`), copied into the key and never deleted; else `<html data-theme-default>` if it is `light|dark|system`; else `system`. `main.tsx` passes `appThemeKey()` and `appDefaultTheme()` to `ThemeProvider`, and `lib/theme-mode.ts` resolves the key at call time, so the script, the provider and the mode hook always agree.
- The legacy migration writes from the script, `main.tsx` and `subscribeThemeMode` (init), never from render.
- Do not edit the `useState` initializer in `theme-provider.tsx` (`localStorage.getItem(storageKey) || defaultTheme`): gv2 patches that exact text.

## Design tokens

Colors are CSS variables on `:root`/`.dark` in `src/styles/globals.css`, stored as FULL colour
values (`oklch(L C H)`, the shadcn v4 format) and consumed as `var(--role)` (e.g. `var(--primary)`;
translucent: `color-mix(in oklch, var(--primary) 40%, transparent)`), or via the Tailwind
semantic classes `@theme inline` maps onto them (`bg-primary`, `text-destructive`, …). **Never
wrap a token in `hsl(...)`** (`hsl(var(--primary))` is invalid: the value is already a full colour). **Never
write a literal hex or a raw Tailwind color** (`bg-green-500`, `#3B82F6`) — it can't be re-themed
and it breaks the live design-preview bridge (`src/lib/archie-design-runtime.ts`), which rewrites
these variables in place.

## `data-agent-*` attributes

You'll see `data-agent-id`, `data-agent-entity`, `data-agent-row`, `data-agent-field` (or
`data-agent-field-state="mixed"|"unresolved"`), and `data-agent-collection-order` on data-bound
markup. These are durable semantic anchors the platform's own tools use to find and edit specific
UI — a table's `data:<Entity>` id names the row *template*, while `data-agent-entity`/
`data-agent-row`/`data-agent-field` on an actual `<tr>` identify one row/field instance. Don't
invent new ones, don't remove existing ones, and don't repurpose one for styling.

## i18n

Copy comes from `react-i18next`. The catalogs actually loaded at runtime are
`src/i18n/locales/<locale>.gen.json` for screen copy and `src/i18n/chrome.<locale>.json` for
copy inside `components/kit/**`, both sealed (see above) — `src/i18n/config.ts` is patched to
import them via a generated barrel. The template's own `locales/en.json`/`es.json` ship in every
app but stop being read the moment that patch lands; don't add copy there expecting it to appear.
Screen copy keys are anchored to a stable id, not the text itself, so editing a string's wording
is safe — renaming its anchor is not, it silently orphans the translation.

## 404 and toasts

- `<NotFound inShell? homeHref? />` (`src/components/NotFound.tsx`): all copy under `notFound.title|body|home|back`
  (English defaults built in, so a catalog that lacks the keys never shows raw keys). Render it with `inShell`
  when the catch-all sits under a layout, so the 404 keeps the sidebar (STATE.17).
- `<Toaster />` is mounted once in `src/main.tsx`, inside `ThemeProvider`. Screens only call `toast` from
  `@/components/ui/sonner`; never mount a second Toaster. Messages are past tense, no "Successfully"/"Oops"/"!" (FEED.23).

## Shared components (`@/components`)

- `<PageHead title description? back? breadcrumb? status? meta? actions? tabs? />`: the one `<h1>` of a signed-in page, full width (HEAD.1-8).
  The page's add action goes in `actions` once; when the collection is empty move it into `<EmptyState action>` (HEAD.16).
- `<StatusChip label tone />`: one chip per record state, same label and tone everywhere (TBL.10). Tones: `ok info pending warn danger neutral`.
- `<ThemeControl variant? />`: light/dark/system via `ThemeProvider` (`archie-ui-theme`, `dark` class). Account menu: `segmented-icons`;
  Settings > Appearance: `preview-cards`. Copy under `themeControl.*` (English fallback built in). Never build a switch + "match system" pair.
- `<EmptyState title description? icon? action? />`: one sentence + the add action when the user can add (STATE.6). No built-in copy.
- `<UploadField variant? label description? uploader onUploaded onError? value? accept? maxSizeBytes? disabled? />` (`src/components/upload-field.tsx`):
  `variant="file"` (any file) or `"avatar"` (round image preview, `image/*`, 5 MB pre-check; override with `accept`/`maxSizeBytes`).
  Real progress (`<Progress>`), cancel, retry, `role="status"` live region, `role="alert"` errors; copy under `uploadField.*`
  (en + es, English defaults built in) with a message per SDK code. It cannot import the SDK (laws), so `uploader` comes from
  `useFileUploader()` in `src/infrastructure/archie/use-file-uploader.ts`, wired in a container/app file. Persist `fileId` (FK to
  `files`), never `url`. The SDK has no `files.delete`. Props are a stable public API: do not rename them.

## Where facts live

- **Routes** — `src/routes.config.tsx` in every shape.
- **Backend shape** (entities, fields, mutations) — the domain layer's generated types (layered),
  or the SDK's own generated types the screens import directly (flat).
- **Copy / language** — the two `.gen`/generated catalogs above; never assume text, read them.
- **Env vars** — read in `src/main.tsx`: `VITE_ARCHIE_PROJECT_ID`, `VITE_ARCHIE_API_URL`,
  `VITE_ARCHIE_ENVIRONMENT`, `VITE_ARCHIE_API_KEY`, `VITE_ARCHIE_IDENTITY_API_KEY`. Set by the
  platform at build/preview time — not committed to this repo.
